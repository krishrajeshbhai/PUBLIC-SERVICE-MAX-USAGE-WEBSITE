# TransitOne — Complete Frontend Implementation Plan

## 0. Frontend mission

The frontend is not just a booking UI.

It has to serve **three experiences from one frontend codebase**:

```text
                         TRANSITONE FRONTEND
                                  │
             ┌────────────────────┼────────────────────┐
             │                    │                    │
             ▼                    ▼                    ▼
       PASSENGER APP        VISITOR EXPERIENCE    EMPLOYEE PORTAL
             │                    │                    │
       Indian users          Foreign users        Transport staff
             │                    │                    │
             └────────────────────┼────────────────────┘
                                  │
                           SHARED DESIGN SYSTEM
                                  │
                           SHARED API LAYER
                                  │
                         SHARED STATE MANAGEMENT
```

The **business logic should not be duplicated**.

Only the experience and presentation should change.

# 1. Frontend technology stack

I recommend:

| Area         | Technology                     |
| ------------ | ------------------------------ |
| Framework    | React                          |
| Language     | TypeScript                     |
| Build        | Vite                           |
| Routing      | React Router                   |
| Server state | TanStack Query                 |
| Local state  | Zustand                        |
| Styling      | Tailwind CSS                   |
| Forms        | React Hook Form                |
| Validation   | Zod                            |
| Maps         | MapLibre GL / Leaflet          |
| Icons        | Lucide                         |
| Animation    | Framer Motion                  |
| i18n         | i18next                        |
| PWA          | Vite PWA                       |
| Testing      | Vitest + React Testing Library |
| E2E          | Playwright                     |

### Why TypeScript?

Because you're building a platform where:

```text
Frontend
      ↓
API
      ↓
Journey
      ↓
Booking
      ↓
Ticket
      ↓
Wallet
```

all depend on shared data structures.

JavaScript will eventually create:

> "Backend says `totalCost`, frontend expects `cost`, another component expects `fare`."

TypeScript catches much of this before runtime.

# 50. Security on frontend

Remember:

### Frontend security ≠ backend security.

Frontend can:

* hide unauthorized UI
* protect routes
* expire sessions
* sanitize display
* avoid storing secrets

But backend must enforce authorization.

Never put:

```text
API secret
payment secret
operator credential
```

in frontend code.

# 54. Critical security rule

The voice assistant must **never bypass authorization**.

This is dangerous:

```text
User says:
"Transfer ₹10,000."
 ↓
AI
 ↓
Payment API
```

Instead:

```text
Voice
 ↓
Intent
 ↓
Authorization
 ↓
Confirmation
 ↓
Authentication challenge if required
 ↓
Backend transaction
```

The AI should propose actions.

The backend decides whether they're permitted.

# The product experience you're actually building

Instead of:

> **"Here's a transportation booking application."**

you are building:

> **"Tell TransitOne what you want to do, and TransitOne handles the complexity."**

A user can say:

**"Take me to college."**

→ TransitOne understands the destination  
→ checks the network  
→ finds the best route  
→ tells them the fare  
→ starts the journey  
→ tracks them  
→ detects delays  
→ proposes alternatives  
→ asks for confirmation when money/actions are involved  
→ shows the ticket  
→ completes the journey.

For an international visitor:

**"I want to go to the Taj Mahal."**

→ TransitOne understands the destination  
→ explains India's transport options  
→ creates the multimodal journey  
→ explains each transfer  
→ provides the ticket  
→ guides them step-by-step  
→ speaks in their language  
→ keeps the itinerary available offline.

And for an older passenger who doesn't want to touch the interface:

**"Where is my bus?"**

→ TransitOne simply speaks back with the answer and optionally opens the live map.

That is the right direction. **Don't build a "chatbot feature." Build a conversational control layer over the entire TransitOne platform.**
