# TransitOne UI Restructuring — Three Separate User Modules

I want you to redesign and restructure the TransitOne frontend. The current design incorrectly combines Passenger App, Visitor Experience, and Employee Portal into one connected UI experience.

Instead, create **three clearly separate application modules** with separate authentication, onboarding, navigation, layouts, dashboards, user flows, and visual experiences.

Do not create one combined homepage where users are simply redirected based on their role.

The product should behave like **three different applications inside one TransitOne ecosystem**.

---

## Core Architecture

```text
                        TRANSITONE ECOSYSTEM
                                │
          ┌─────────────────────┼─────────────────────┐
          │                     │                     │
          ▼                     ▼                     ▼
    PASSENGER APP        VISITOR EXPERIENCE      EMPLOYEE PORTAL
          │                     │                     │
    Passenger Users       International Visitors    Staff & Operators
          │                     │                     │
          ▼                     ▼                     ▼
   Passenger UI System      Visitor UI System      Operations UI System
          │                     │                     │
          └─────────────────────┼─────────────────────┘
                                ▼
                        SHARED BACKEND APIs
                                │
                        SHARED DESIGN TOKENS
                                │
                           TRANSITONE
```

These are three separate modules.

The UI must not feel like:

```text
One application
+
Different menus
```

It should feel like:

```text
One TransitOne platform
↓
Three different products
↓
Three different user experiences
```

## IMPORTANT IMPLEMENTATION RULES

* Do not redesign this as one combined dashboard.
* Do not reuse Passenger navigation inside Visitor or Employee modules.
* Do not reuse Passenger authentication for employees.
* Do not make Employee Portal mobile-consumer styled.
* Do not make Visitor Experience feel like a daily commute application.
* Keep backend APIs and core domain models reusable.
* Separate the modules at the routing, shell, authentication, navigation, and feature levels.
* Use a shared design token system and shared API client.
* Maintain one backend platform but three clearly independent frontend experiences.
* Create polished production-quality UI for all three modules.
* Ensure all screens have loading, empty, error, and responsive states where relevant.

The final result should demonstrate:

> **One TransitOne ecosystem with three distinct users, three separate authentication systems, three application modules, and three purpose-built UI experiences.**
